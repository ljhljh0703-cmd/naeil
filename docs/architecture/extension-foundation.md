# 기능 확장 기반

사용자 요청: 사진의 원칙을 검토하여 naeil의 기능 확장 지침으로 적용하고 Vault에 기반을 저장한다. 이 문서는 저장소 작업 지침에 연결한 실행 기준이다. Vault 정본 승격, 제품 기능 구현, 외부 검증 도구 설치를 뜻하지 않는다.

## 1. 적용하는 원칙과 근거의 한계

**적용:** 기능별 책임·입출력·실패 범위를 정하고, 기존 동작을 지키는 검사를 변경 위험에 맞춰 실행한다. 동시성·재시도 등 복잡한 상태 변경은 필요하면 형식 검증까지 올린다.

**보정:** 사진의 ‘54%에서 98%’는 Anthropic의 일반 버그 탐지율이 아니다. Opum AI 개발자가 버그를 심은 사례 5개에서 평가 항목 충족률을 측정한 자체 평가다. 개발자는 두 조건 모두 심어 둔 버그를 찾아 수정했다고 설명한다. 검증의 범위·추적 가능성·근거 산출 등에 차이가 있었다. 시간 약 2.4배, 토큰 약 2.2배도 해당 실험의 평균 비율이며 naeil의 예상 비용·효과로 쓰지 않는다.

사진의 정확한 ‘Agent Formalize’ 도구는 미확인이다. 관련 커뮤니티 도구를 공식 제품으로 취급하거나 자동 설치하지 않는다. 실제 Anthropic의 연구는 별도의 RISC-V/Rocq 연구이며 제한된 명세와 가정 아래의 증명이다.

## 2. 한 앱 안에서 책임을 나눈다

현재 규모에서는 단일 앱·데이터베이스를 유지하면서 공개 계약과 자료 쓰기 소유자를 분리한다. 다음 기능이 닿는 경계부터 정리한다. 디렉터리를 나누는 것만으로 장애가 격리되지는 않는다. 프로세스 종료·메모리 고갈·공유 데이터베이스 장애는 여러 기능에 영향을 줄 수 있다.

아래는 **책임 배치 기준**이다. 현재 코드가 모두 이 모양으로 분리됐다는 뜻이 아니다.

| 경계 | 맡는 일 | 다른 곳에 넘기는 일 / 현재 상태 |
|---|---|---|
| 인증·작업공간 | 출입증 확인, 신뢰할 주체·작업공간 전달 | 표시명만으로 권한 부여 금지. 기존 기반 있음 |
| 프로젝트·마일스톤·일감 | 자기 자료 변경, 규칙 검사, 변경기록 | 외부 실행기를 직접 기다리지 않음. 기존 기반 있음 |
| 오늘 화면·보드 | 조회·입력·선택 상태 | 권한·저장 규칙은 서버가 판정. 기존 기반 있음 |
| 공동 작업방·보고 | 대화/보고와 지시·일감의 참조 | 원본 위치 결정 필요. 기능안 단계 |
| 실행기 연결 | 실행 요청, 시간 제한, 취소, 상태 관측, 결과 수신 | 일감 완료·사람 승인 자동 판정 금지. 기능안 단계 |
| 예약·전달 | 정해진 시점에 기존 명령 호출, 누락/실패/중복 관리 | 별도 업무 규칙 복제 금지. 기능안 단계 |
| 외부 자료 연계 | 출처 참조·변환·가져오기 경계 | 자료 원본과 앱 업무 상태를 섞지 않음. 연결별로 판단 |

모듈의 최소 계약은 `책임 / 입력 / 출력 / 자료 쓰기 소유자 / 오류 / 재시도 / 취소 / 복구`다. 당장 쓰지 않는 미래 기능의 인터페이스를 미리 전부 만들지는 않는다.

## 3. 신호와 쓰기의 규칙

- **명령:** 상태 변경 요청. **조회:** 상태를 바꾸지 않는 읽기. **이벤트:** 이미 확정된 변화의 통지. 같은 프로세스 안의 즉시 호출은 타입이 있는 함수로 충분하다.
- 외부 실행·예약처럼 지연될 수 있는 흐름에서는 요청/실행 식별자, 원인 참조, 작업공간, 대상과 예상 판본을 전달 계약에 둔다. 인증된 주체는 서버가 정하며 본문의 임의 주체 값을 신뢰하지 않는다.
- 요청 재전송 방지와 업무 자체의 중복 방지를 구분한다. 같은 요청 식별자는 같은 내용을 재생하고 다른 내용이면 충돌로 다룬다. 별도 요청으로 같은 원문을 가져오는 중복은 출처 참조 등 도메인 규칙으로 처리한다. 보존 기간과 정리 이후 행동을 명시한다. 기존 24시간 재시도 보존을 영구적인 ‘딱 한 번’ 보장으로 표현하지 않는다.
- 업무 자료·필수 변경기록·재시도 응답은 필요한 경우 하나의 트랜잭션으로 확정한다. 성공 응답과 성공 이벤트는 확정 전에 내보내지 않는다.
- 저장 후 전달만 하면, 저장 직후 프로세스가 죽는 순간 통지가 유실될 수 있다. 유실 복구가 필요한 흐름에서는 **전달 대기 항목도 업무 자료와 함께 저장**한 뒤 재전송한다. 상대가 이미 받았을 수 있으므로 수신 측도 중복을 처리한다. 이 방식은 현재 구현 완료가 아니다.
- 외부 호출은 제한 시간을 두고 트랜잭션 밖에서 실행한다. 일시 오류와 권한/입력 오류를 구분하고, 재시도 횟수·대기·종료 상태를 둔다. 취소 요청이 왔어도 외부 실행이 중단됐다는 증거가 없으면 ‘중단 완료’로 표시하지 않는다.

## 4. 확장 때 지킬 불변조건

| 조건 | 반례로 확인할 상황 |
|---|---|
| 인증된 범위 밖의 자료를 읽거나 바꾸지 않는다 | 다른 작업공간 ID, 위조 주체/세션 문자열, 권한 없는 등록/실행 |
| 같은 요청 재시도와 같은 업무 원문의 중복을 각각 처리한다 | 응답 유실 후 재전송, 같은 키의 다른 본문, 새 키로 같은 출처 재수입 |
| 필요한 업무 변경·기록·재시도 응답이 함께 성공/실패한다 | 업무 저장 후 로그 실패, 기록 후 재시도 응답 저장 실패 |
| 오래된 실행이 최신 상태를 덮지 않는다 | 재할당/취소/새 실행 이후 도착한 옛 결과, 순서가 뒤바뀐 이벤트 |
| 접수·실행·보고·완료·승인은 서로 다른 사실이다 | 보고만 올린 실행을 완료로 처리, 실행 종료를 사람 승인으로 처리 |

생성자·담당자·판정자도 구분한다. 사람, 지속되는 에이전트 역할, 개별 실행 세션을 표시명 하나로 합치지 않는다. 현재 `held_by`와 `ai_working` 표시는 일반 소유권 잠금이 아니다. 선택적 판본 검사도 모든 경로의 경합 방지를 보장하지 않는다.

화면 변경에는 프로젝트 A에서 입력한 값이 프로젝트 B에 남아 제출되는 경계도 포함한다. 서버의 범위 검사와 화면 상태 초기화를 둘 다 확인한다.

## 5. 현재 코드에서 재현한 보완 항목

확인 입력: `a19ae618ff682939602f2c2d79c48755b86af707`의 앱 소스. 조회한 `origin/main`의 `990e24c1011e314664ddced2b315ec38ee56de86`과 차이는 CI 파일뿐이었다. 이 비교는 이후 저장소 상태까지 보장하지 않는다.

`src/db/store.ts`의 `Store.createTask`는 일감 INSERT 뒤 `this.log`를 따로 호출한다. `src/app.ts`의 idempotent 경로는 `Idempotency-Key`가 있을 때 트랜잭션을 감싸지만, 키가 없으면 `run()`을 직접 호출한다. API 계약에서 키는 선택이다.

실제 Store를 가져와 메모리 데이터베이스의 로그 INSERT에 실패를 주입했다.

| 조건 | 남은 일감 | 생성 기록 |
|---|---:|---:|
| 정상 대조 | 1 | 1 |
| 직접 호출 + 기록 저장 실패 | 1 | 0 |
| 명시적 트랜잭션으로 감싼 호출 + 같은 실패 | 0 | 0 |

**판정:** 부분 저장 가능성을 Store 실행 수준에서 재현했다. 무키 HTTP 경로와의 연결은 소스 분석이며 HTTP 요청 자체를 실행한 결과는 아니다. 제품 수정은 아직 적용하지 않았다. 이 기록을 해결 완료로 바꾸려면 원자성 보완과 해당 경로의 회귀 증거가 필요하다.

**해결 (S1, 2026-11-05):** `createTask`의 일감 INSERT와 생성 기록을 하나의 트랜잭션으로 묶었다. `test/atomic.test.ts`가 기록 저장 실패를 주입해 저장소 직접 호출, 재시도 열쇠 없는 주소 호출, 열쇠 있는 주소 호출 모두 일감 0개(열쇠 있는 경로는 재시도 응답도 0개)임을 확인한다. 수정 전 같은 시험은 열쇠 없는 두 경로에서 실패했다.

일감 생성·보고 연계 쓰기를 확장하기 전에 이 틈을 보완한다. 관련 없는 문구·화면 개선을 이 문제 때문에 전부 중단할 필요는 없다. 다른 쓰기 경로가 안전하다는 전수 판정도 하지 않았다.

재현 코드·로그·입력 지문은 Vault 반환 패킷 `wiki/projects/work-hub-returns/extension-foundation-v1/`이 가리키는 외부 근거 폴더에 보존한다. 실제 출입증·실사용 데이터베이스·서버에는 접근하지 않은 시험이다.

## 6. 위험에 맞춰 검증한다

| 변경 | 필요한 확인 | 더 올리는 조건 |
|---|---|---|
| 문구·색·간격 | 관련 화면, 필요 시 좁은/넓은 폭 | 자료/입력 상태가 바뀌면 다음 단계 |
| 일반 기능·자료 계약 | 타입·입출력 계약·영향 회귀·권한/실패 경계 | 상태 경합·재시도·여러 쓰기가 얽히면 다음 단계 |
| 동시 수정·재시도·취소·시간 만료·권한 전이 | 불변조건·상태 전이·실패 주입·실행 순서 바꾸기 | 조합이 많아 반례를 찾기 어렵다면 속성 검사·모델 검사 검토 |
| 모델 검사/형식 증명이 필요한 복잡한 부분 | 명세·가정·한정 범위·코드 대응·실제 검사기 출력 | 발견한 반례를 제품 코드 회귀 검사로 연결 |

형식 검증은 자동으로 항상 켜는 절차가 아니다. 구체적인 성질과 검증할 모델이 있고, 신뢰할 검사 도구를 사용할 수 있을 때 해당 부분에 적용한다. 외부 도구의 설치·비용·권한은 실제 허용 범위 안에서 별도로 확인한다. 모델을 검사했다는 결과와 제품 코드 전체가 안전하다는 주장은 구분한다.

**증거의 최소 항목:** 입력 판본/지문, 주장하는 성질, 가정과 탐색 범위, 사용 도구/버전, 실행 명령과 종료 코드, 원문 출력, 실패해야 하는 대조 사례, 남은 미확인. 증명/모델의 가정과 실제 실행 환경이 다르면 그 차이를 먼저 적는다.

통과만 확인하지 말고 원래 오류 또는 의도적으로 깨뜨린 작은 대조에서 검사가 실패하는지도 확인한다. 성공 결과를 만들기 위해 명세를 약화하거나 검사 대상을 제거하지 않는다. 필요한 검사를 통과한 뒤 입력·코드가 바뀌지 않았다면 이유 없이 전체 검사를 반복하지 않는다.

## 7. 다음 기능에 쓰는 짧은 변경 계약

```text
기능/완료 조건:
변경 범위와 기존 동작:
자료 소유자·공개 입력/출력·원본 위치:
주체·작업공간·등록/실행/판정 권한:
지켜야 할 불변조건:
중복·재시도·시간 만료·취소·오래된 결과 처리:
실패 시 복구·필요한 자료 이전/되돌림:
검증 수준과 반례:
실행 결과 / 미실행 / 남은 한계:
```

첫 적용 대상은 일감 생성의 원자성 보완, 이어서 실제 에이전트 1종의 보고 1건·일감 1건 왕복이다. 실제 연결 지원 여부를 확인하고, 같은 전송 재시도·응답 유실·권한 오류를 검사한다. 화면용 모의 데이터는 실제 연결 완료 증거로 쓰지 않는다.

공동 작업방의 운영 보고 원본을 앱 데이터베이스에 둘지 Vault 기록에 둘지는 아직 미정이다. 기존 일감/기록 원칙과 조정해 정해야 하며, 이 문서는 후보를 자동 채택하지 않는다. 시각 디자인 선택도 이 지침과 별도다.
